2. **P1 — Quality success could be mistaken for success within the frozen cost budget. ADDRESSED by explicit separate field.** Inherited `research/research_gn_nn_completion_r3/src/score.py:282–283` sets `joint_success` from physical/material gates and complete accounting, while the next line separately checks wall/LU/RHS caps. Thus a measured wall overrun can coexist with `joint_success=True`. Current R4 `src/score.py:51,54,76` adds `budgeted_joint_success = joint_success and accounted_within_budget` to rows and summaries. Use this field for a budgeted success claim; `joint_success` remains the explicitly separate quality result. No inherited historical source was changed by this review.

3. **P2 — Explicit seal can disagree with the CLI split used to guard TEST access. OPEN at snapshot; parent implementing repair.** `experiments/score_predictions.py:7–12` gates on `a.split`, but forwards the arbitrary supplied `--seal` to `score()`. `src/score.py:26` delegates truth opening to the inherited scorer before reading the seal itself at `:27`. A TEST seal supplied with `--split val` therefore misses this freeze check and can label the destination as VAL. This is a protocol/API mismatch, not evidence TEST was exposed. Minimal fix: inspect the supplied seal's actual splits before any scoring call, require them to match the requested split, and apply the method-freeze requirement to actual TEST contents. Put the guard in the R4 scoring API too if that API is the supported entry point.
