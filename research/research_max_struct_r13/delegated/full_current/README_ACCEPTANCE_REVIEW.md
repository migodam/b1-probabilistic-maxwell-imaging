Findings below preserve the original review evidence, followed by this explicit resolution record rather than silently erasing it.

1. **Vector physical work is available but not mapped to the scorer's canonical names.** `vector_adapter.py:68-70` records `physical_LU`/`source_RHS`, and `vector_adapter.py:95-99` records `adjoint_RHS`. In contrast, `score_results.py:219-220` looks only for `LU` and `actual_complex_RHS`, as do final cost extraction/totals at `score_results.py:250-260`. Vector LU/RHS and candidate LU curves therefore become unknown despite existing counters. Explicitly canonicalize those fields or have the scorer use the declared alternative names. Total actual physical complex RHS is source_RHS plus adjoint_RHS under this adapter's stated convention; retain the two components too. Do not count projector/current-block RHS as physical RHS. No scientific method change is needed.

2. **Fresnel periodic physical audits are not yet matched.** `physics_inputs.py:94-116` accepts `audit_every` through `**kwargs` but does not use it. The inherited solver physically validates only initial/stage-end materials (`research/research_max_struct_r8/src/fresnel_solver.py:32-34,75`). Its final stage has 150 updates (`physics_inputs.py:113-115`), so a deadline can interrupt that stage after 50 or 100 updates with no corresponding paid physical candidate. Projection methods audit every 50 (`run_experiment.py:198-201`). Either supply an explicitly new per-call audit hook without restarting PR, or name the measured baseline audit schedule as unmatched and limit comparative claims. Do not silently weaken or relabel the mature algorithm.

3. **The main runner's classic Austria dispatch remains pending.** In the reviewed version, scalar paths always call R6 `arm_config` (`run_experiment.py:125-144`), whose material-box contract is [.02,20]. Classic Austria uses [0,20] and needs `classic_auxiliary_config` (`physics_inputs.py:119-143`) plus explicit equal-area selection. The existing full-current adapter is already compatible and was narrowly validated. Parent has acknowledged this pending runner patch; do not launch classic auxiliary cases through the reviewed old scalar branch.

4. **A missing final queue receipt is not a terminal-state proof.** Seal construction reads only canonical `queues/{campaign}/RECEIPT.json` (`seal_results.py:63-64`). If it is missing, queue_pending/queue_running become null; `validate_seal` rejects only truthy values (`seal_results.py:25-29`). Under the immutable STATUS queue design (`finite_queue.py:25-38`), a live queue may have STATUS files and no final canonical receipt. Parent authorization must therefore inspect explicit terminal evidence and full expected-task accounting, or the seal validator needs an explicit unknown-state rejection/declared partial-run override. Size/mtime validation protects prediction files but does not establish process termination by itself.

5. **Failed controller recovery costs remain unknown where not observed.** Parent reported the historical Windows rename failure, four aborted children with unknown exit CPU, and an 18-task continuation. This review did not operate on those processes. Preserve those failed-attempt records separately from successful continuation costs and retain unknowns. `score_results.py:250-260` correctly avoids imputing unknown CPU, but its current single-campaign cost extraction will not automatically add costs from a separate failed controller history. Any final campaign total must distinguish measured successful/continued work, known failed-attempt work, and unrecoverable unknown costs. Do not present a known sum as a complete total.

## GT isolation and offline scoring

Accepted: `score_results.py:182-199` validates explicit parent authorization and the prediction seal before loading result arrays or any truth. Truth loading is only inside `load_truth`, invoked afterward (`:58-66,:197-202`). The online runner reads only the task's public input (`run_experiment.py:50-51`), and no truth path appears in its inference/control flow. This source review has not called the truth loader or scorer.

The seal inventories results, queues, manifest and public inputs (`seal_results.py:45-50`), rejects changed sizes/mtimes and directory contents (`:30-39`), and stays unauthorized by default (`:64`). This is a provenance snapshot, not a cryptographic certificate. Main code/runtime provenance still needs the parent's separate immutable code freeze because these source files are not themselves added by this seal routine.

Missing/failed tasks remain expected rows; valid candidates from failed runs are explicitly partial (`score_results.py:217-235,:252-260`). Available-only means expose their denominators. Paired statistics use a fixed seed and group repeated conditions by object (`:83-97`). The lookup currently assumes one task per `(case_id,method)`; if future cold/NN or repeated seeds reuse that exact key, they will overwrite each other in paired/figure lookups. Encode conditions in distinct case IDs plus shared object_id, or extend those lookup keys before such a manifest is used.

Current fresh amplitude normalization is `max(truth)-host`, shared across methods for the same case and applied only after sealing (`score_results.py:48-65,:76-80`). Declaring it before confirmation is compatible with GT isolation; it is not an online selection signal. For cross-object/cross-grid comparability, an additional `RMSE/(upper-lower)` column would use the fixed public box range and avoid a denominator that changes with cell-averaging amplitude. Keep the existing declared metric and label both; do not replace it after observing fresh results.

Candidate metadata and materials are zipped and assumed to have contiguous consistent candidate IDs (`score_results.py:207-233`). The reviewed runner produces exactly that convention (`run_experiment.py:77-84`). An independent scorer consistency check would be useful before accepting externally produced or hand-edited task bundles, but no such malformed bundle was observed here.
